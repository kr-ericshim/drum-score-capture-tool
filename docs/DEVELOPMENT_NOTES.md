# 개발 기록

Drum Sheet Capture를 만들면서 부딪힌 문제와 해결 과정을 정리한 문서입니다. 숫자와 날짜는 커밋 기록과 릴리스 노트에서 가져왔습니다.

- 기간: 2026년 2월 시작, v0.3.1(2026-10-20)까지 커밋 316개, 릴리스 태그 43개
- 구성: Electron 데스크톱 앱 + Python 영상 처리 엔진(FastAPI, OpenCV), macOS·Windows 설치 파일

## 1. 음표 인식 대신 원본 이미지를 다시 배치하기로 한 이유

v0.2까지는 악보가 보이는 영상 화면을 페이지 이미지로 캡처해 PDF에 그대로 넣었습니다. v0.3에서는 목표를 바꿔, 드럼 레슨에서 받는 악보처럼 한 줄에 4마디 안팎, 한 페이지에 여러 줄이 정리된 A4 악보를 만들기로 했습니다. 실제 레슨용 PDF를 재서 줄 수, 오선 간격, 제목 위치를 기준으로 삼았습니다.

방법은 두 가지를 놓고 고민했습니다.

- 음표 인식(OMR)으로 악보를 새로 그리기
- 영상에 나온 악보 이미지를 줄 단위로 잘라 정리한 뒤 A4에 다시 배치하기

2026-10-06에 두 번째 방식으로 정했습니다. 음표 인식은 한 번 틀리면 PDF에 틀린 음표가 그대로 찍히고, 사용자가 그 오류를 영상과 일일이 비교해 찾기 어렵습니다. 이미지를 옮기는 방식은 원본이 흐리면 PDF도 흐리다는 단점이 있지만, 영상에 없던 내용이 생기지는 않습니다.

범위도 함께 좁혔습니다. 한국 드럼 커버 영상에서 흔한 "악보 한 줄이 통째로 다음 줄로 바뀌는" 영상을 기본 지원 대상으로 잡았습니다. 옆으로 흐르는 악보는 드물어서 범위에서 뺐습니다. 반투명 판 위의 악보처럼 결과를 보장할 수 없는 영상은 PDF를 만들지 않고 지원하지 않는다고 알리게 했습니다.

이 파이프라인은 2026-10-09에 처음 들어갔고, v0.3.0(2026-10-20)에서 기본 출력이 됐습니다.

## 2. Windows에서만 PDF 다시 만들기가 실패하던 문제

증상: Windows에서 검토 화면의 **PDF 다시 만들기**를 누르면 서버가 500 오류를 냈습니다. 제목에 한글이 들어간 작업에서 주로 생겼고, macOS에서는 재현되지 않았습니다.

원인: Python은 파일을 열 때 인코딩을 지정하지 않으면 운영체제 기본값을 씁니다. macOS는 UTF-8이지만 Windows는 시스템 코드 페이지라서, 한글 제목이 든 작업 JSON을 저장할 때 `'charmap' codec` 오류가 났습니다. ffmpeg·yt-dlp 출력을 읽는 부분도 같은 문제가 있었습니다.

해결: 인코딩을 지정하지 않은 곳을 모두 찾아 UTF-8로 고정했습니다(JSON 입출력 12곳, 외부 프로그램 출력 12곳). 테스트도 Windows에서 통과하도록 고쳤습니다. `/tmp` 경로를 하드코딩한 곳, JSON 안에서 이스케이프된 경로, 경로 구분자 차이가 원인이었습니다. 확인은 macOS에서 기본 인코딩을 ASCII로 강제한 상태로 backend 테스트 전체를 돌려서 했습니다. 이후 새 코드는 텍스트를 읽고 쓸 때 항상 `encoding="utf-8"`을 쓰도록 규칙으로 정했습니다.

## 3. 릴리스 시간을 약 25분에서 약 5분으로 줄이기

릴리스 워크플로는 태그를 올릴 때마다 backend 테스트 1,462개를 macOS와 Windows에서 다시 돌렸습니다. 같은 커밋을 CI에서 이미 검사했는데도 한 번 더 기다려야 했습니다.

바꾼 내용:

- backend 테스트를 pytest-xdist로 병렬 실행합니다. CI 한 번이 macOS 약 11분, Windows 약 17분이 됐습니다.
- `main`에는 작업 브랜치에서 검사가 끝난 커밋만 fast-forward로 올리므로, `main` push와 문서만 바뀐 커밋은 CI를 건너뜁니다.
- 릴리스 워크플로는 태그가 가리키는 커밋에 대해 CI가 두 운영체제에서 모두 통과했을 때만 backend 테스트를 건너뜁니다. CI 기록이 없거나, 실패했거나, 조회 중 오류가 나면 예전처럼 테스트를 다시 돌립니다.

v0.3.1 릴리스는 약 5분 만에 끝났습니다(이전 약 25분).

## 4. 결과를 바꾸지 않고 PDF 만들기 빠르게 하기

PDF 만들기 시간을 측정해 보니, 프레임을 비교하는 단계에서 같은 계산을 두 번 하고 있었습니다. 각 프레임 조각을 "현재 프레임"으로 한 번, 다음 비교에서 "이전 프레임"으로 또 한 번 처리했습니다(흑백 변환, 오선 간격 측정, 오선 제거, 재생 표시 감지).

한 번 계산한 결과를 다음 비교에 넘기도록 바꾸고, 같은 식의 중복 작업을 세 군데 더 줄였습니다. 조건은 "만들어지는 PDF는 한 비트도 바뀌지 않는다"였습니다. 변경마다 이전 결과와 같은지 확인했습니다. 예를 들어 캐시를 쓴 판정과 쓰지 않은 판정이 같은지 비교하는 테스트를 추가했고, 다른 변경은 무작위 입력 6,025개에서 이전 함수와 결과가 같은지 확인했습니다.

결과: 3분짜리 합성 영상에서 PDF가 8~9초(약 10%) 빨리 나오고, 검토 화면의 다시 만들기가 1.4초 빨라졌습니다.

## 5. 앱을 닫아도 처리기가 남아 CPU를 쓰던 문제

증상: macOS 설치 앱을 닫은 뒤에도 Python 처리기가 CPU를 약 100% 쓰며 남아 있었습니다. 부모 프로세스가 사라져 PPID가 1인 상태였습니다.

원인: Electron은 종료할 때 처리기에 SIGTERM을 보내고 바로 끝납니다. 그런데 처리기(uvicorn)는 진행 중인 요청이 끝날 때까지 제한 없이 기다렸습니다. 앱이 강제 종료되거나 오류로 꺼지면 처리기를 끝낼 방법이 아예 없었습니다.

해결:

- 정상 종료 대기를 최대 3초로 제한했습니다.
- 앱이 처리기를 실행할 때 stdin 파이프를 연결하고, 처리기는 그 파이프가 닫히면 스스로 종료합니다. 앱이 어떻게 꺼지든 파이프는 닫히므로 강제 종료와 오류 상황도 처리됩니다.
- 처리기가 띄운 ffmpeg 같은 하위 프로세스도 함께 끝냅니다. macOS는 프로세스 그룹 전체를 종료하고, Windows는 `taskkill /T`를 씁니다.

macOS 설치 앱에서 앱을 닫으면 처리기도 함께 끝나는 것을 확인했고, v0.3.1에 넣었습니다.
